# Aizanoi Analytics — Verified Audit (2026-08-17)

This audit cross-checks external LLM reviews against the actual repository. Repository code is the source of truth; findings that depended on guessed production state or nonexistent modules were rejected or qualified.

## Executive summary

**Current assessment: 7.8/10 after this hardening branch.**

The project has a distinctive product identity, a surprisingly careful backend/security boundary for a hobby project, and two serious historical-world experiments. The main technical liability is the large single-file `frontend/index.html`: it mixes the shell, styles, window manager, routing, app templates and most UI behavior. That does not justify a framework rewrite, but it does justify gradual extraction after the current shell is stable.

The most valuable immediate work was not adding features. It was removing verified failure modes, correcting factual/operational inconsistencies, and adding regression coverage so later agents cannot silently reintroduce them.

## What was verified and fixed in this branch

### P0/P1 reliability

- **Independent boot escape hatch** added before the large application scripts. The desktop can become reachable even if a later application script fails before registering the normal boot close handler.
- **Malformed CSS removed** from the window-menu dropdown section. There was an orphaned declaration block and unmatched closing brace after `.win-menu-dropdown`.
- **Rome WebGL fallback** added. Browsers with WebGL disabled/unavailable no longer depend on a throwing renderer module; renderer import/initialization failures show a user-facing fallback instead.
- **Game lifecycle leak reduced** in Snake and Brick Breaker. Their timers stop when the containing game DOM is removed, preventing orphan intervals after switching games or closing the Games window.
- **Google fallback configuration fixed**: `.env.example` now documents `GOOGLE_API_KEY`, matching `backend/server.js`.

### Product/content correctness

- Removed dead **Market** entries from frontend icon/app mappings. `/market/` remains a deliberately removed product and must not be resurrected without an explicit product decision.
- `robots.txt` no longer blocks `/market/`; production can return HTTP 410 and crawlers are allowed to observe that removal signal.
- Corrected Aizanoi heritage copy: Aizanoi is on Türkiye's UNESCO World Heritage Tentative List since 2012; the previous claim that it was inscribed on the World Heritage List in 2025 was incorrect.
- Replaced an unverified privacy promise about third-party model training with neutral provider-terms wording.
- Standardized user-facing **Aizanoi OS** naming.
- Added **Aizanoi TV** to the desktop/Start launcher while keeping its current coming-soon content.
- Fixed the Start-menu **Control Panel** action so it opens the actual Control Panel instead of My Computer.
- Migrated several primary Start-menu icons to the custom Aizanoi SVG family.

### Accessibility baseline

- Window minimize/maximize/close controls now expose button semantics, keyboard focus and accessible labels.
- Start button, Start-menu actions and dynamic taskbar items now expose basic keyboard activation.
- This is a baseline improvement, not a claim of WCAG conformance.

### Repository hygiene

- Added MIT `LICENSE` and package metadata because the repository describes itself as open source.
- Added lightweight GitHub Actions CI.
- Added regression tests covering shell inline-script syntax, boot fallback, removed Market references, UNESCO copy, Control Panel routing, backend env/config invariants, terminal non-shell dispatch and game timer cleanup.
- `AGENTS.md` now documents the minimum validation commands expected before deployment.

## External review findings accepted

### 1. Monolithic frontend is the largest maintainability debt

Accepted. `frontend/index.html` is a large single-file SPA containing CSS, HTML templates, routing, app registries and window-management logic. This increases the blast radius of a syntax/runtime mistake.

**Decision:** do not rewrite with React/Vue/Next. Stabilize first, then extract in small mechanical phases:

1. CSS to one external stylesheet.
2. Route/app metadata to a data module.
3. Window manager/router to a shell module.
4. Individual app wiring to small modules.
5. Keep vanilla JS unless a real requirement appears that a framework solves better.

### 2. Rome lacked graceful WebGL failure handling

Accepted and fixed.

### 3. Canvas games could leave timers running

Accepted and fixed for Snake and Brick Breaker. Mines does not have the same continuous timer pattern.

### 4. `.env.example` and backend Google key name disagreed

Accepted and fixed.

### 5. Mobile Rome controls are incomplete

Accepted and still open. The main Aizanoi OS shell has substantial mobile handling, while Late Antique Rome is effectively keyboard/mouse-first. This should be solved in the Rome experience itself, not by complicating the desktop shell.

### 6. Social-preview metadata is incomplete

Accepted. The shell has dynamic title/description/canonical/OpenGraph text, but a production-quality `og:image`/`twitter:card` asset is still needed. A route-aware prerender strategy is a separate architectural decision.

### 7. Unknown SPA routes behave like soft 404s

Accepted. Generic nginx SPA fallback means unknown paths can receive the shell with HTTP 200. Production routing should eventually whitelist known SPA routes or otherwise return a true 404 for unknown URLs.

### 8. Basic keyboard accessibility was incomplete

Accepted; baseline fixes are included here. Full focus management, menu roles and modal/dialog behavior remain future work.

## External review findings rejected or qualified

### “AI provider failover/API keys are client-side” — rejected

The current repository routes AI requests through the Node/Express backend. Provider keys are read from server environment variables. The frontend does not contain the reported multi-provider key chain.

### “Developer password/system prompt security is client-side” — not supported by current repo

No evidence for the described frontend developer-auth/system-prompt manager was found in the current source. Do not implement a speculative backend migration for code that is not present.

### “Terminal executes a shell and therefore needs sandboxing” — rejected as stated

The backend uses a `SAFE_COMMANDS` dispatch table rather than passing arbitrary user input to `child_process.exec`. Path handling also applies explicit sandbox/path checks. Continue testing this invariant; do not replace it with a real shell.

### “Add a shared secret header to the public frontend” — rejected

A static secret shipped to a public browser is not a secret. If anonymous AI abuse becomes material, use server-side quotas, Turnstile/challenge flows, provider dashboards/alerts or another mechanism that does not expose a reusable credential in frontend code.

### “Immediately migrate to Three.js/Babylon/React” — rejected for now

The historic experiences already contain custom WebGL work and a data-driven Rome structure. A migration before product/engine convergence would create two migrations instead of one. First decide and consolidate the shared historical-world lifecycle/data model.

### “Add CSV/file upload now” — rejected for current product scope

The product intentionally has no accounts or file upload. A future anonymized HR dataset workflow could be valuable, but it adds privacy/security/storage concerns and should be an explicit product decision, not an audit side effect.

### “Market is an active product” — rejected

Market is deliberately removed. Dead references were cleanup debt, not evidence it should return.

### “Production lacks HSTS/CSP because the sanitized nginx example lacks it” — qualified

The public `infra/nginx` file is explicitly a sanitized example, not proof of the live production configuration. Security headers must be verified against the actual server before production changes are proposed.

## Architecture direction

### Aizanoi OS shell

Keep the desktop metaphor and vanilla implementation. The shell should become progressively more modular without changing behavior. The correct end-state is **not** “generic SaaS SPA”; it is a maintainable Aizanoi OS shell.

A useful future structure is:

```text
frontend/
  index.html
  css/aizanoi-os.css
  js/core/router.js
  js/core/window-manager.js
  js/core/desktop.js
  js/apps/chat.js
  js/apps/games.js
  js/apps/control-panel.js
  data/app-registry.js
```

Do this mechanically, one extraction at a time, with CI and browser smoke tests after each extraction.

### Aizanoi AI

The current short system prompt is appropriately scoped: HR + People Analytics, including practical/soft HR as well as Excel/SQL/Power BI/DAX/Power Query/Python. Do not inflate it into a giant rulebook.

Future improvements, in order:

1. Streaming responses for perceived latency.
2. Better provider timeout/health telemetry.
3. Optional lightweight role/context selection if it materially improves answers.
4. Abuse protection only if real traffic shows a need.

### Ancient World

Treat `/ancient-world/` as the launcher/hub. Keep individual 3D worlds as independent experiences so a rendering failure cannot take down Aizanoi OS.

There are currently two generations of historical-world implementation:

- `/historic-world/` — mature self-contained Aizanoi WebGL prototype.
- `/ancient-cities/rome-410-476/` — newer modular/data-driven Late Antique Rome implementation.

Do not merge them blindly. The useful convergence target is a shared **data/lifecycle contract**, not necessarily one huge renderer. Preserve the Rome `data/city.js` style separation; later identify reusable movement/input/fallback/POI pieces.

### Games

Keep them small and isolated. Every game must expose a lifecycle/cleanup path before more games are added. The current timer cleanup is a stopgap; a future loader API such as `{mount(container), destroy()}` would be cleaner.

## Remaining roadmap

### P1 — next meaningful engineering phase

1. **Deploy and browser-smoke-test this hardening branch.** Verify boot, desktop, Start menu, Control Panel, AI, Games, Historic World and Rome.
2. **Add real mobile controls to Late Antique Rome.** Touch look + movement controls; keep desktop pointer-lock behavior unchanged.
3. **Create a production social preview asset** (`1200×630` PNG/JPEG) and add `og:image`, `twitter:card=summary_large_image`, `twitter:image`, `og:type`, `og:site_name`.
4. **Fix true HTTP 404 behavior for unknown routes** in production nginx while preserving known SPA routes/deep links.
5. **Begin mechanical frontend extraction** only after the production smoke test remains stable: first external CSS, then route/app registry.

### P2 — quality/product polish

- Complete menu/context-menu keyboard/focus behavior.
- Add explicit destroy hooks to game modules.
- Add lightweight frontend error reporting/telemetry if blank-screen debugging remains difficult.
- Revisit AI streaming and longer answer handling.
- Add a simple PWA manifest only when installability is actually useful.
- Connect Aizanoi TV after the YouTube channel exists; avoid placeholder API complexity today.

### P3 — later product work

- Converge reusable Ancient World engine/lifecycle pieces after at least two worlds demonstrate what is truly shared.
- Route-specific server-rendered/prerendered landing HTML if SEO/content strategy proves valuable enough to justify it.
- HR data upload only after an explicit privacy/security/product design phase.

## Things not to do now

- Do not resurrect Market.
- Do not rewrite the site in React/Vue/Next just because `index.html` is large.
- Do not migrate both historical worlds to a new 3D engine before deciding what must actually be shared.
- Do not add a browser-visible “secret” to protect the public AI endpoint.
- Do not add more games until lifecycle cleanup has a consistent contract.
- Do not make factual historical claims without a source trail.

## Deployment note

This branch changes source only. Production server files and credentials are intentionally outside this repository. Before production deployment: take a timestamped backup, review the Git diff, run the documented CI-equivalent checks, deploy frontend/backend files without replacing `.env`, and smoke-test the live routes.
